# wave-far-normals NOTES

## 요약 (최종 상태, 2026-10-04)

아래 본문은 시간순 작업 기록이다. 이 요약은 최종적으로 남은 것과 그 이유만 모았다.

### 문제 → 원인 → 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 근경 파도와 원경 물결 방향이 X자로 엇갈림 | 거리 LOD가 Gerstner 파도의 높이와 **노멀을 함께** 꺼서, 원경에는 텍스처 방향을 따르는 노멀맵만 남았다 | 메시가 지운 파도 기울기를 픽셀 셰이더가 같은 식으로 채움(step1) + 노멀맵 바람 정렬(step3) |
| 원경에 마름모 격자 (step1의 부작용) | 같은 대비의 사인 줄무늬 4개가 원근으로 압축돼 교차. 파장당 4 → 2px까지 그리면 글린트가 모아레로 증폭 | 픽셀 구간을 16 → 8px에서 끝내고, 그보다 작은 파도는 기울기 분산 σ²로 바꿔 글린트를 넓힘(step2) |
| 오션 그리드에서 잔물결 조명이 무늬와 어긋남 | 오션 그리드 UV가 OBJ 평면과 앞뒤 반대(v = −Z)라 노멀맵 G 채널을 거꾸로 읽음 | 그리드 UV를 v = +Z로 통일. Flow direction, 각도표, 정렬 회전도 함께 정리 |
| 해를 등진 원경의 나무·하늘 반사가 회색으로 뭉개짐 | σ²만큼 큐브맵 mip으로 하늘 반사를 흐린 처리가 형상을 지움 | 반사 흐림 제거(step4). 글린트 확산은 유지 |
| 해가 수평선에 걸린 장면에서 반짝임 띠 폭을 조절할 방법이 없음 | 원경 확산이 물리식 고정값 | Light 창 `Far spread`(σ² 배율, 0~3) |

### 최종 구성

- **파도마다 3구간** (Debug 6: R / G / B)
  - 메시: 정점 셰이더가 변위와 노멀을 계산한다.
  - 픽셀 노멀: 메시가 지운 몫 `(1 − vertexFade)`을, 파장당 16 → 8px에서 끝나는 `pixelFade`까지 픽셀 셰이더가 다시 계산한다.
  - 거칠기: 나머지를 `σ² = Σ rough·(kA)²/2`로 모아 글린트·스펙큘러 지수를 `n / (1 + n·σ²·FarSpread)`로 넓힌다. 에너지 정규화로 넓어진 만큼 어두워진다.
- **Align to wind:** 레이어별 옵션이고 프리셋에 저장된다. 텍스처마다 측정한 무늬 축을 Wave 1 방향으로 돌린다.
- **두 메시의 UV 통일:** u = +X, v = +Z
- **캡처 도구:** `--preset-file`, `--far-waves`, `--align-ripples`, 해를 등진 `ocean_away` 샷
- **비용:** GPU 0.19 → 0.20 ms (1280×760, Release)

### 시도했다가 폐기한 것

| 시도 | 폐기 이유 |
|---|---|

| σ²만큼 하늘 반사 흐림(큐브맵 mip) | 반사 형상을 지움(해를 등진 시점) |

### 남은 참고 사항

- 기능을 꺼도 이전 커밋과 비교하면 글린트 주변에 최대 10 / 평균 ≤ 0.05의 차이가 난다. 셰이더 구조가 바뀌면서 컴파일 결과가 달라진 것이고, 눈으로는 구분되지 않는다(step2 참고).
- Sunset 프리셋은 태양 `Intensity`가 0이라 태양 원반과 글린트가 보이지 않는다. 의도한 설정인지 확인이 필요하다.

## 문제

- 사용자 테스트 중 ocean 그리드에서 "근경과 원경의 물결 방향이 X자로 엇갈려 보인다"는 지적이 나왔다.
- 원인: 정점 셰이더의 거리 LOD가 파도마다 `파장 × 8 ~ 14` 거리에서 Gerstner 파도를 끈다.
  - 이때 끄는 건 높이(`offset`)와 노멀(`normalSum`) **둘 다**다. 노멀도 `amplitude × fade`로 계산되기 때문이다.
  - 기본 크기(Wave 1 = 1.6)에서는 약 20 유닛 너머가 평평한 면 + 노멀맵만 남는다.
- 근경 무늬 방향은 Wind direction이 정하고, 원경 무늬 방향은 노멀맵 텍스처(예: "Diagonal ripples")가 정한다. 둘이 서로 연결돼 있지 않아서 X자가 된다.

## 접근

- 높이는 계속 끈다. 정점 간격이 파장보다 넓어지면 메시가 파도를 표현할 수 없기 때문이다.
- 노멀은 픽셀마다 계산할 수 있어서 정점 밀도와 상관이 없다. 그래서 같은 4개 파도의 기울기를 **픽셀 셰이더에서** 다시 계산한다.
- 근경을 바꾸지 않도록, 파도 i의 노멀 기여를 fade 가중치 w로 나눴다. 기여는 w에 선형이다.
  - VS: `w = vertexFade`
  - PS: `w = (1 − vertexFade) · pixelFade`
  - 둘을 합치면 근경에서는 VS 노멀과 같고, 원경에서는 PS 노멀이 된다.
- VS의 Q 항은 `q·kA = steepness·fade / 4`라서 PS에서도 같은 식(`steepness·w / 4`)을 쓴다.
- 위상은 변위 전 local 위치(`restPosLocal`, VS→PS로 새로 전달)로 계산한다. VS와 같은 기준이라 전환 구간에서도 마루 위치가 맞는다.
- 공용 함수 `WaveVertexFade`는 `shaders/Waves.hlsli`로 뺐다. VS는 이 함수를 호출하도록만 바꿨고 결과는 비트 단위로 같다(아래 OFF 회귀).

## 픽셀 페이드 기준 (실험)

`footprint = max(|ddx(xz)·D|, |ddy(xz)·D|) / λ`는 한 픽셀이 파도 진행 방향으로 덮는 파장 수다. 방향별로 계산하므로, 카메라 쪽으로 뻗은 마루는 더 멀리까지 남는다.

`captures/horizon_threshold.jpg`(Basic ocean_wide 수평선 2배 확대)에 세 기준을 비교했다. 행 순서: before, 2px, 3px, 4px.

| 기준 (파장당 픽셀, 시작 → 0) | 결과 |
|---|---|
| 4 → 2 (나이퀴스트) | 수평선까지 줄무늬는 이어지지만, 고대비 간섭무늬(moire)가 생김 |
| 6 → 3 | 조금 줄었지만 여전히 촘촘한 고대비 줄 |
| **8 → 4 (채택)** | 수평선 바로 앞의 고주파 줄이 사라지고 노멀맵으로 넘어감. 바람 방향 마루는 원경까지 유지 |

- 나이퀴스트(2px)만 지키면 될 것 같았지만 실제로는 부족했다.
- 태양 글린트(power 300~800)와 Fresnel 반사는 노멀에 매우 민감하다. 그래서 해상 가능한 범위의 노멀 변화도 화면에서는 고대비 줄로 증폭된다.

## 사용자 테스트 1 → 문제: 마름모 격자

- 사용자 시점(ocean 저각)에서 중·원경에 **마름모 격자**가 생겨 이전보다 부자연스러웠다.
- **원인:**
  1. 원경에는 조명만 남는다. 조명은 높이가 아니라 기울기(∝ 높이/파장)에 반응하고, Simple 모드는 네 파도의 높이/파장을 비슷하게 유지한다. 그래서 네 사인 줄무늬가 같은 대비로 보인다.
  2. 이전 Basic 프리셋의 spread가 90°였다. Wave 4가 바람과 거의 반대로 진행해 줄무늬가 격자로 겹쳤다. **사용자가 spread를 20~30°로 낮추자 격자가 사라지는 것을 확인했다.**
  3. 실제 바다에서 해상도보다 작은 파도는 마루가 아니라 표면 거칠기(넓은 반짝임 띠, 흐린 반사)로 보인다. step1은 이런 파도를 마루로 그리거나 지웠다.
- 조사한 대안: 원경 노멀 약화(A), 기울기 분산 → 거칠기(B), 노멀맵 바람 정렬(C), FFT / tiling & blending(D, 범위 밖)
- 사용자가 B → C 순서를 골랐다. 각 단계를 같은 조건으로 캡처해 비교한다.

## 캡처 조건 고정 — `--preset-file`

- 사용자가 테스트 중에 프리셋을 새 값으로 저장했다(22:55). before/step1은 그 전 값으로 찍혔다.
- 단계 비교가 공정하려면 같은 값이 필요하다. 그래서 그 전 값을 `capture_presets.txt`로 커밋하고, `--preset-file`로 읽어서 찍는다. `assets/shader_presets.txt`(사용자 작업 파일)는 건드리지 않는다.
- 이 플래그로 이전 셰이더를 돌려 찍으면 before와 **픽셀 차이 0**이다. 플래그 자체가 결과를 바꾸지 않는다는 뜻이다.

## step2 — 기울기 분산 → 거칠기 (B)

- 파도마다 세 구간: 메시(정점) / 픽셀 노멀 / **거칠기**
  - 픽셀 구간은 더 일찍 끝낸다(16 → 8px). 4 → 2px까지 그리면 네 줄무늬가 격자로 보인다.
  - 픽셀이 해상하지 못하는 몫 `(1 − vertexFade)·(1 − pixelFade)`은 분산으로 바꾼다: `σ² += rough · (kA)²/2` (사인 기울기의 평균 제곱)
- σ²의 사용처 (Bruneton 2010, Toksvig / LEAN mapping과 같은 아이디어):
  - 태양 글린트와 Blinn-Phong 지수 `n' = n / (1 + n·σ²)`. 에너지 정규화 `(n'+2)/2`도 n'로 계산해 넓어진 만큼 어두워진다.
  - 하늘 반사: 반사 방향은 기울기 편차의 약 2배로 퍼진다. 큐브맵 mip 중 텍셀 하나가 `2σ`를 덮는 단계로 `SampleLevel` 한다(HDR 하늘은 mip 11단계). 하드웨어 mip보다 선명해지지는 않는다.
    - → **이후 변경(step4):** 반사된 나무·하늘 형상까지 지워서 제거했다.
- **Debug 6 확장:** 파랑 = 거칠기 구간(`captures/step2_debug6`)
- **OFF 회귀: 최대 10 / 평균 ≤ 0.05.** 0이 아닌 이유를 실험으로 좁혔다.
  - 거칠기 연산을 상수 0으로 지워도, 환경맵 mip 호출을 빼도 최대 10이 그대로였다.
  - 남은 차이는 원경 함수를 struct 반환으로 정리한 것뿐이다. OFF에서는 `0 ×`로 수학적으로 영향이 없다.
  - 결론: 셰이더 구조가 바뀌어 드라이버가 같은 식을 다른 명령 순서로 컴파일했고, pow 300~800의 글린트가 그 반올림 차이를 증폭했다. 눈으로는 구분되지 않는다.
  - 함께 고친 것: `n / (1 + n·0)`은 GPU에서 근사 역수로 나눠 정확히 n이 아닐 수 있다. 그래서 σ² = 0이면 원래 값을 그대로 쓰도록 분기했다.
- **결과:** 수평선 쪽 원경이 격자 대신 넓은 반짝임 띠와 흐린 하늘 반사가 된다(`captures/horizon_steps_*.jpg` 3번째 줄).
  - 이전 Basic 값은 Wave 4가 가팔라서(높이/파장 0.044) σ²가 커 원경이 많이 밝아진다.
  - → **이후 변경(step4):** 흐린 하늘 반사는 없앴다. 넓은 반짝임 띠는 남겼다.

## step3 — 노멀맵 바람 정렬 (C)

- **텍스처 방향 측정:** `tools/measure_normal_orientation.ps1`
  - 렌더러가 쓰는 DDS를 texconv로 PNG로 바꾸고, 512²로 줄여 구조 텐서를 계산한다.
  - 두 가지를 구한다: 저장된 기울기 n.xy의 주축(slope), 무늬의 공간 기울기 주축(pattern)

| 맵 | slope 축 | pattern 축 (사용) | 이방성 |
|---|---|---|---|
| 0 Diagonal ripples | −75.0° | 75.8° | 0.43 |
| 1 Soft swell | −89.9° | −83.8° | 0.31 |
| 2 Soft chop | 74.0° | −70.4° | 0.32 |
| 3 Long streaks | −86.6° | −89.2° | 0.49 |
| 4 Fine chop | 70.5° | −67.3° | 0.30 |

→ **이후 변경(UV 수정):** 위 표는 수정 전 오션 그리드(v = −Z) 기준이다. 그리드를 v = +Z로 바꾼 뒤 다시 측정하니, 모든 맵에서 slope 축과 pattern 축이 일치했다. 코드의 각도표는 이제 −76 / 84 / 70 / 89 / 67°다.

- **발견 1 — 메시마다 UV v 방향이 반대다.** 오션 그리드는 v = −Z, 벤치 평면 OBJ는 v = +Z다.
  - 정렬 결과를 위에서 내려다본 샷으로 검증하다가 각도가 거울상으로 나와서 알게 됐다.
  - 회전은 메시의 v 방향(`g_MeshParams.x`)을 받아 처리한다.
  - → **이후 변경:** 오션 그리드 UV를 OBJ와 같게 맞추면서 `g_MeshParams`와 `vSign`을 제거했다.
- **발견 2 — 맵 0/2/4는 slope 축과 pattern 축이 X축 기준 거울상이다.** 오션 그리드 기준으로 G 채널 규약이 반대라는 뜻이다(벤치 평면에서는 맞는다). 조명의 기울어지는 방향이 무늬와 어긋나 있지만, 이번 범위 밖이라 별도 과제로 남긴다.
  - → **이후 변경:** 원인은 텍스처가 아니라 오션 그리드 UV였다. curl 검사로 다시 보니 1, 3번 맵도 같은 상태였다. 아래 "버그 수정 — 오션 그리드 UV 방향"에서 해결했다.
- **회전:**
  - uv를 월드 정렬 좌표 `(u, vSign·v)`로 바꿔 `R(−a)`로 돌린 뒤 되돌린다.
  - 샘플한 기울기는 `R(a)`로 평면 좌표로 되돌린다.
  - 스크롤은 회전 전 uv에 그대로 더해서 Flow direction UI의 의미가 유지된다.
  - 회전각 = Wave 1 방향 − 텍스처 축. 축은 180° 주기라서 ±90° 안에서 작은 쪽으로 돈다.
- **검증 (top 샷, Debug 1 노멀맵을 크롭해 같은 도구로 측정):**
  - Sunset: 82.5° → 19.4° (바람 20°)
  - Tropical: 95.4° 회전 (예상 96°)
  - Basic: −76.6° (Wave 1 = −74°)
  - 절대 각도에는 크롭이 작아서 생기는 ±10° 정도의 측정 잡음이 있다. 회전량은 예측과 1° 안에서 맞는다.
- **회귀:** 플래그 없이 찍으면 step2 대비 최대 10 / 평균 ≤ 0.05(위와 같은 컴파일 차이). 옛 프리셋은 정렬 OFF다.
- **GPU 시간:** 정렬 + 원경 ON 0.20 ms, 원경 OFF 0.19 ms(`captures/gpu_step3_on_off.jpg`)

## 버그 수정 — 오션 그리드 UV 방향

- **문제:** 오션 그리드(`Model::InitializeGrid`, 코드로 생성한 800×800 수면)는 UV를 `v = 0.5 − z·0.5`(이미지 아래쪽 = −Z)로 깔았고, 벤치 평면 OBJ는 이미지 아래쪽 = +Z다.
  - 같은 노멀맵이 오션에서만 앞뒤로 뒤집혀 붙었다.
  - 셰이더는 G 채널을 항상 +Z 기울기로 읽기 때문에, 오션에서는 Z 방향 기울기가 반대로 해석됐다. 물결의 밝은 면과 어두운 면이 무늬와 어긋났다.
- **확인:** 노멀맵은 실제 요철에서 나왔다면 회전 성분(curl)이 0이어야 한다. 다섯 장 모두 벤치 평면 배치에서 일관됐다(상관 0.72~0.93). 텍스처와 OBJ는 정상이고 오션 그리드만 반대였다.
- **수정:**
  - `Model::InitializeGrid`의 v를 `0.5 + z·0.5`로 바꿨다(OBJ와 같은 방향).
  - 이 방향을 전제로 한 코드도 맞췄다:
    - `FlowControls`: 월드 흐름 = (−u, −v)
    - `kNormalMaps.rippleAxisDeg`: 부호 반전
    - 정렬 회전의 메시별 분기 `g_MeshParams` 제거
    - `tools/measure_normal_orientation.ps1`의 Z 방향
  - 재측정하니 모든 맵에서 slope 축과 pattern 축이 일치했다(예: 맵 0은 −75.0° / −75.8°).
- **검증:** `captures/uvfix_before` vs `uvfix_after` (사용자 현재 프리셋)
  - 벤치 평면 9장은 **픽셀 차이 0**
  - 오션 6장만 바뀌었다(최대 240 / 평균 5~15).
  - 비교: `compare_uvfix/*.jpg`, 근경 확대 `captures/uvfix_closeup_sunset.jpg`
  - 수정 전에는 잔물결이 울퉁불퉁 얼룩져 보였고, 수정 후에는 벤치 평면처럼 결이 고른 물결로 보인다.
- **주의:** 프리셋에 저장된 흐름 값(UV 속도)은 그대로라, 오션에서 잔물결이 흐르는 방향이 앞뒤로 바뀐다. Flow direction UI는 이제 두 메시 모두에서 실제 방향을 표시한다.

## 사용자 테스트 2 → 문제: 해를 등진 원경의 반사가 죽음

- 사용자 시점(해를 등지고 나무·집을 보는 저각)에서 Far waves를 켜면 수평선 근처에 비치던 나무와 하늘이 회색 단색으로 뭉개졌다.
- **검증 사각지대:** 고정 캡처 샷의 ocean 두 장이 모두 해를 향하고 있었다. 그 방향에서는 글린트 확산으로 오히려 밝아져서 문제가 드러나지 않았다. → 해를 등진 샷 **`ocean_away`**(높이 1.6, pitch 8°, yaw 214.5°)를 추가했다. Tropical은 해가 yaw 236.4°라 이 샷에서는 해 쪽을 본다.
- **가설 1 — Fresnel(낮은 각도의 반사율 저하):** 원경 기울기를 빼고 평균 노멀로 Fresnel을 계산해 봤다. `ocean_away` 원경 띠 밝기는 basic 74.6 → 74.6, sunset 83.5 → 83.6, tropical 138.5 → 138.6으로 **효과가 없었다.** 원인이 아니라서 되돌렸다.
- **가설 2 — 하늘 반사 흐림:** 흐림만 빼고 찍자 나무·하늘 반사가 돌아왔다. 밝기가 아니라 **비친 형상이 지워진 것**이 문제였다. 큐브맵의 높은 mip은 형상 대신 평균색만 남긴다.

## Far spread — 원경 글린트 확산 세기 (Light 창)

- 사용자 요청: 태양이 수평선에 걸린 장면을 연출할 때 원경 반짝임 띠의 폭을 조절하고 싶다.
- Light 창 Sun Glint 섹션의 기존 `Sharpness`와 `Strength`는 근경과 원경에 똑같이 적용된다. 그래서 원경에서만 넓어지는 정도를 조절하는 **`Far spread`**(0~3)를 추가했다.
  - 해상도보다 작은 파도의 기울기 분산 σ²에 곱하는 배율이다. 1 = 물리값, 0 = 확산 없음(날카로운 글린트), 1보다 크면 반짝임 띠가 더 넓어진다.
  - 프리셋 키는 `farGlintSpread`다(없으면 1). cbuffer에 `g_FarParams.x`를 추가했다.
- **회귀:** 기본값 1에서 Sunset과 Tropical은 이전 캡처와 픽셀 차이 0이다. Basic은 사용자가 그 사이 프리셋을 다시 저장해서 비교에서 제외했다.
- **데모:** `captures/far_spread_sunset_horizon.jpg`. 데모를 위해 Sunset 태양 세기를 1.2로 올린 임시 프리셋을 썼고, 태양은 고도 4°의 수평선에 있다. 0 / 1 / 2.5 순으로 수평선을 따라 반짝임 띠가 넓어진다.
- **참고 — Sunset에 태양이 안 보이는 이유:** Sunset 프리셋의 태양 `Intensity`가 0이다(커밋 `09dba1b`부터). 원반과 글린트 모두 이 값에 비례한다. HDR 노을 하늘은 사진 속 태양을 잘라냈기 때문에 태양이 전혀 보이지 않는다.
- **참고 — Basic이 가장 하얗게 번지는 이유** (해를 향한 `ocean_wide` 원경 띠의 밝기):
  - 고정 샷에서 태양이 화면 앞에 오는 프리셋은 Basic뿐이다. Sunset은 태양 세기가 0이고, Tropical은 태양이 카메라 뒤에 있다.
  - Basic의 노출이 +0.07 EV로 가장 높다(Tropical −0.81, Sunset −1.2). **노출만 −0.81로 낮추면 흰 픽셀 비율이 18%에서 0%가 됐다.**
  - 그 밖에 Glint Strength 1.5, F0 0.103, 상대적으로 큰 σ²(0.022 vs 0.012)와 낮은 Sharpness(362)도 번짐을 키운다.
