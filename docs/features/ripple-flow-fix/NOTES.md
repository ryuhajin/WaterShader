# ripple-flow-fix — 바람 정렬한 노멀맵의 흐름 방향 (회고 기록)

> 2026-10-04 · feature/ripple-flow-fix

캡처 조건은 이전 feature와 같다(1280×720, `t = 12s`, 고정 샷 6개, 무인 모드). 프리셋은 수정 당시 main의 `assets/shader_presets.txt`다.
재현: `WaterShader.exe --capture-feature ripple-flow-fix --capture <label> [--align-ripples on] [--debug 1]`

---

## 문제

preset-themes 튜닝 중 수식을 보다가 발견했다. "Align to wind"를 켠 노멀맵 레이어는 Water 창 Flow direction 다이얼과 다른 방향으로 흐른다.

## 원인 — 다이얼도 회전 수식도 아닌, 스크롤을 더하는 순서

```
수정 전:  p = R(−a)·(uv·s) + v·t
```

- `RotateRippleUv`는 샘플 위치를 −a만큼 돌린다. 그러면 무늬가 수면 위에서 +a만큼 돈다. 이건 맞다.
- 그런데 스크롤 `v·t`를 회전한 **뒤에** 더했다. 오프셋이 회전된 무늬 좌표계 안에서 적용된다.
  - 무늬 위의 한 점 p0는 `uv = R(a)·(p0 − v·t)`에 보인다. 따라서 수면 위 이동 방향은 `−R(a)·v`다.
- 다이얼(`FlowControls`)은 "저장값 v → 수면 위 흐름 −v"를 표시한다. 정렬을 끈 레이어(a = 0)에서는 맞고, 켜면 a만큼 어긋난다.
- 셰이더 주석은 처음부터 "스크롤은 평면 uv 기준이라 Flow direction의 의미가 유지된다"였다. 의도는 맞았고 구현만 틀렸다.

**고칠 곳은 셰이더다.** 다이얼을 `−R(a)·v`로 맞추면, 바람 방향(= a)을 바꿀 때마다 같은 저장값의 실제 흐름이 함께 돌아간다. 저장값이 "수면 위 흐름"이라는 의미를 잃는다.

```
수정 후:  p = R(−a)·(uv·s + v·t)   →  수면 위 이동 = −v
```

## 검증 (AI agent)

### 흐름 방향 측정

- **도구:** `measure_drift.ps1`. 같은 샷의 두 캡처 사이에서, 중앙 영역의 무늬가 몇 픽셀 이동했는지를 절대차 합이 최소인 정수 이동으로 찾는다.
- **조건:**
  - `--debug 1`(노멀맵 레이어 A만 표시), `top` 샷(바로 위에서 내려다봄: 화면 오른쪽 = +X, 아래 = −Z)
  - t = 12s와 14s. 캡처 시각은 상수라, 14s 캡처는 `kCaptureTime`을 임시로 바꾼 빌드로 찍고 되돌렸다.
- **파도 높이 0 프리셋(`measure_presets.txt`):**
  - 처음엔 원래 프리셋으로 쟀다. 정렬 OFF에서도 다이얼과 6~13° 어긋났다. Gerstner 파도의 수평 이동이 무늬 이동에 섞이기 때문이다.
  - 그래서 main 프리셋에서 파도 높이만 0으로 둔 파일을 `--preset-file`로 썼다. 파도 방향은 남겨 두어 정렬 각도는 그대로다.

| 프리셋 | 다이얼 방향 | 정렬 각도 a | 예측 (수정 전) | 수정 전 OFF / ON | 수정 후 OFF / ON |
|---|---|---|---|---|---|
| Basic | 49.0° | −29° | 20.0° | 49.9° / **19.2°** | 49.9° / **49.9°** |
| Sunset | 29.3° | −64° | −34.7° | 29.5° / **−34.4°** | 29.5° / **29.5°** |
| Tropical | −49.3° | −84° | −133.3° | −49.4° / **−133.2°** | −49.4° / **−49.4°** |

- 수정 전: 정렬 ON의 흐름은 예측대로 다이얼에서 a만큼 돌아가 있었다(오차 1° 이내).
- 수정 후: 정렬 ON/OFF 모두 다이얼 방향과 1° 이내로 맞는다.
- 측정 캡처: `captures/m_{before,after}_{on,off}_t{12,14}/` (local-only)

### 정렬 OFF 회귀

- 캡처 18장이 비트 단위로 같지는 않다. 최대 차이 9/255, 평균 차이 최대 0.041/255, 2 넘게 다른 픽셀 최대 0.22%.
  - 같은 exe로 두 번 찍으면 파일 해시가 같다(캡처는 결정적). 따라서 차이는 수식 변경에서 온다.
  - (1, 0) 회전은 수학적으로 항등이지만, 컴파일러가 `uv·s + v·t`를 fma로 묶는 순서가 바뀌어 반올림이 달라진다. uv 값이 큰 ocean 샷에서 차이가 조금 더 크다.
  - `R(uv·s) + R(v·t)` 형태(선형성으로 같은 값)도 시도했지만 역시 비트 단위로 같지 않았다. 그래서 읽기 쉬운 한 번 회전 형태로 남겼다.
- 정렬 ON(`captures/before_align` vs `after_align`)은 t = 12s의 무늬 위치가 달라져 크게 다르다. 의도한 변화다.

## 영향

- 정렬을 켠 프리셋은 무늬가 놓이는 위상이 바뀐다. 이제 다이얼 방향으로 흐른다.
- preset-themes의 흐름 값(Basic A, Sunset A)은 다이얼 기준으로 정한 값이라, 이 수정으로 의도대로 흐르게 된다.
