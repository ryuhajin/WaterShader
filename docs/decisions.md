# 기술 의사결정 로그

이 문서는 프로젝트 진행 중 내린 **기술적 선택과 그 이유**를 시간 순서로 기록합니다.
나중에 "왜 이렇게 했지?"가 떠오르면 여기를 먼저 봅니다.

각 항목은 다음 형식을 따릅니다:

> **결정** — 한 줄 요약
> **이유** — 왜 이 선택을 했는가
> **대안** — 검토했지만 채택하지 않은 옵션
> **(선택) 재검토 트리거** — 어떤 조건이면 이 결정을 다시 볼지

## 2026-04-28 · 메인 기술 스택: DirectX11 + HLSL

**결정** — UE5 머티리얼 그래프가 아닌, **DirectX11 + 순수 HLSL**로 셰이더를 직접 작성한다.

**이유** — 펄어비스 아트_셰이더 디자인 인턴십 공고가 "HLSL을 이용한 엔진 셰이더 제작"을 담당업무로, "HLSL 기반 셰이더 결과물 완성"을 필수 역량으로 명시함. UE5 노드 그래프보다 평가자가 기술 역량을 직접 확인하기 쉬움.

**대안** — UE5 머티리얼만 제출 (HLSL 검증 약함), Unity Shader Graph (공고와 거리 멈), SDF 함수 매뉴얼만 제출 (셰이더 결과물 부족).

**재검토 트리거** — DX11 셋업이 Day 3까지 끝나지 않으면 UE5 Custom Node로 fallback 검토.

---

## 2026-04-28 · 메인 주제: 호수/수면 (폭포 아님)

**결정** — 폭포 대신 **스타일라이즈드 호수/수면**을 메인 산출물로 한다.

**이유** — 10일 안에 완성도를 확보하기 좋고, UV 스크롤 / 노멀 블렌딩 / fresnel / foam / SDF ripple 등 아트 셰이더 핵심 기법을 두루 보여줄 수 있음. 폭포는 vertical flow와 alpha clipping이 추가로 필요해 위험.

**대안** — 폭포 (시간 부담), 환경 + VFX 조합 (산만), SDF 단독 라이브러리 (셰이더 결과물 부족).

---

## 2026-04-28 · 헬퍼: DirectXTK 사용

**결정** — 텍스처 로딩, 프리미티브, 카메라 헬퍼는 **DirectXTK**로 처리한다.

**이유** — Direct3D 11 C++용 공식 헬퍼 클래스 모음. 부트스트랩에 들어가는 시간을 셰이더 작업 시간으로 돌릴 수 있음. 출처: [Microsoft DirectXTK](https://github.com/microsoft/DirectXTK)

**대안** — 직접 작성 (시간 낭비), DirectX-Graphics-Samples (학습 곡선 큼).

---

## 2026-04-28 · 파라미터 UI: ImGui

**결정** — 셰이더 파라미터 조절 UI는 **ImGui**로 만든다.

**이유** — 데모 영상에서 "파라미터 조절 가능"을 시각적으로 보여주는 데 가장 빠른 도구. vcpkg에 포함되어 있어 통합 비용 낮음.

---

## 2026-04-28 · UE5 포팅: 보너스 항목

**결정** — UE5 머티리얼 포팅은 **모든 main 산출물이 끝난 뒤**에만 시도한다.

**이유** — 제출 우선순위는 `DX11 원본 HLSL > 영상/문서 > UE5 보너스`. UE5에 시간을 쓰다가 main이 미완으로 끝나는 위험 회피.

---

## 2026-04-29 · 문서 구조: feature 단위 + 브랜치 매칭

**결정** — 문서는 일자별이 아닌 **기능 단위**(`docs/features/<name>/`)로 분리하고, 브랜치 이름과 1:1 매칭한다.

**이유** — 셰이더는 작은 기능들이 누적되며 만들어지므로, 일자 단위 문서보다 기능 단위 문서가 추후 기능 추가/수정 시 참조하기에 유리. 브랜치 ↔ 폴더 매칭으로 추적성 확보.

**대안** — 일자별 daily 로그 (PLAN2.md 제안, archive에 보존됨), 통짜 BREAKDOWN 문서 (검색 어려움).

상세 규칙: `CONVENTIONS.md`

## 2026-10-04 · 선택 기능은 별도 셰이더 변형으로 (OCEAN_DETAIL)

**결정** — 기존 프리셋 화면에 영향을 주면 안 되는 셰이더 기능은 `#if OCEAN_DETAIL`로 감싸 같은 파일을 두 번 컴파일하고, 값이 켜졌을 때만 그 변형을 바인딩한다.

**이유** — 값이 0이라 실행되지 않는 분기만 추가해도 드라이버의 명령어 배치가 바뀌어, 기존 캡처 18장 중 9장이 일부 픽셀에서 1~4 레벨 달라졌다. 변형을 분리하자 해시까지 같아졌다. 회귀를 "해시 동일"로 검증할 수 있다는 점이 이 프로젝트의 비교 방식(캡처 전후 대조)에 중요하다.

**대안** — 분기만 추가하고 1~4 레벨 차이를 허용(회귀 판정이 눈대중이 됨), 별도 셰이더 파일(공통 코드 중복).

**재검토 트리거** — 변형이 3개 이상 필요해지면 정의 조합 관리 방식을 다시 정한다.

## 2026-10-04 · hero는 프리셋이 아니라 고정 카메라 샷

**결정** — 포트폴리오 메인 컷 "hero"는 고정 샷 `ocean_hero`로 두고, Basic / Sunset / Tropical이 같은 위치를 공유한다.

**이유** — 사용자 의도는 "한 구도에서 테마마다 다른 태양·색"이었다. 처음에는 4번째 셰이더 프리셋으로 잘못 구현했다가 되돌렸다(ocean-hero NOTES 4절).

**대안** — 4번째 프리셋 테마 Hero(구도와 물 값이 한 테마에 묶여 다른 테마와 비교할 수 없음).

## 2026-10-04 · 고해상도 렌더의 LOD는 720p 기준

**결정** — `--render-size`로 렌더할 때 먼 파도 구간 경계와 노멀맵 mip을 720p 창 기준으로 맞춘다(footprint × 렌더 높이/720, mip bias log2).

**이유** — 이 경계들은 화면 픽셀 기준이라, 2560×1440에서는 고운 명암이 늘고 축소해 보면 회색으로 평균되어 창에서 고른 화면과 달라졌다(밝기 표준편차 37 → 32). 고해상도 컷의 목적은 "창에서 고른 화면을 더 선명하게"이므로 기준을 맞췄다.

**대안** — 해상도에 따라 세밀도가 달라지는 것을 그대로 둠(물리적으로는 맞지만 고른 화면과 다름), 720p로 렌더해 확대(가장자리가 흐림).
